# MySnipTool 技术方案

> Windows 轻量截图工具 · 常驻内存目标 ≤ 20MB · 无 Electron / 无运行时依赖
> 版本：v1.0 设计稿 ｜ 状态：待评审，未写代码

---

## 0. 结论摘要

| 项 | 决策 |
|---|---|
| 最终技术栈 | **Rust + 原生 Win32（windows-rs）**，不使用 WebView、不使用任何 UI 框架 |
| 空闲常驻 | 实测目标 3–6 MB（私有工作集），红线 20MB 有充足余量 |
| 分发形态 | 单个 exe（2–4MB），无安装器、无运行时依赖 |
| 界面形态 | 托盘 + 一个自绘历史面板 + 一个设置对话框 + 一个框选遮罩，全部 GDI 绘制 |
| 实时框架约束 | 禁止引入 tokio / async runtime / 任何 WebView |

三者对比的简短回答：**内存上 Tauri ≥ Qt > WinUI3，没有一个是「天然」满足 20MB 的**。Tauri 只要创建窗口就会拉起 3–5 个 `msedgewebview2.exe` 子进程；Qt Widgets 精调后可卡在 20MB 边缘但不稳；WinUI 3 直接超一个数量级。

## 1. 内存对比与选型

### 1.1 先对齐口径（这一步不做，后面全是扯皮）

Windows 上「内存」至少三种读法，差异可达 3–5 倍：

| 口径 | 含义 | 取值方式 |
|---|---|---|
| **私有工作集 / Private Bytes** | 本进程独占的物理页，最接近「真实成本」 | VMMap、`PrivateMemorySize64` |
| **工作集 Working Set** | 私有 + 共享（user32/gdi32/comctl32 等系统 DLL 页） | 任务管理器「内存」列 |
| **提交大小 Commit** | 私有 + 已保留的分页文件配额 | `PagedMemorySize64` |

**建议验收口径：私有工作集 ≤ 20MB，同时工作集 ≤ 30MB。** 本方案在两种口径下都能过；Qt 会在工作集口径上翻车，WinUI3 两种都过不了。

### 1.2 空闲态内存对比（典型工程估算，非绝对保证）

| 方案 | 空闲常驻 | 面板/对话框打开后 | 部署体积 | 依赖 |
|---|---|---|---|---|
| Rust + Tauri 2（托盘常驻，窗口延迟创建） | 6–10 MB（仅 Rust 进程） | **75–150 MB**（+3~5 个 `msedgewebview2.exe`） | 3–8 MB + 需 WebView2 运行时 | Edge 运行时（Win10 需引导安装） |
| C++ + Qt6 Widgets（动态链接） | 16–26 MB | 22–35 MB | exe 小 + Qt DLL 25–40 MB | Qt DLL、VC 运行库 |
| C++ + Qt6（静态链接） | 12–20 MB | 18–28 MB | 8–15 MB | 无（但 LGPL 需商业授权或合规处理） |
| C# + WinUI 3 | **70–130 MB** | 90–180 MB | 80–150 MB | WindowsAppRuntime |
| C# .NET 8 NativeAOT + 裸 Win32（参考项） | 8–14 MB | 12–20 MB | 4–8 MB | 无 |
| **Rust + 原生 Win32（推荐）** | **3–6 MB** | **6–9 MB** | **2–4 MB** | **无** |

> 上述数字为工程经验区间，必须在目标机型上用 VMMap 实测确认（见 §10 验证计划）。同一方案在不同 Windows 版本、不同显卡驱动、是否有杀软注入之间波动可达 ±40%。

### 1.3 逐项点评

**Rust + Tauri 2 —— 被误解的「轻量」**

Tauri 的宣传语是"前端用系统 WebView，所以包体小"。这句话只说了一半：

- 省掉的是 **Chromium 打包体积**（约 150MB），不是内存。
- Windows 上 WebView2 是**多进程架构**：一个 browser 进程 + 一个 GPU 进程 + N 个 renderer 进程。即使只渲染一个 400×500 的列表，实测常驻也在 60–120MB。
- 唯一能救的做法是**启动时不建窗口**（`tauri::Builder` 不配 `windows`，需要时用 `WebviewWindowBuilder` 动态创建）。这样空闲态只剩 Rust 宿主进程 6–10MB —— 数字上过线了，但代价是：
  - 面板首次打开要冷启动 WebView2，200–500ms 白屏；
  - 框选遮罩如果也用 webview 画，全屏透明窗口 + 实时鼠标追踪的**输入延迟和显存占用**都不可接受，最终仍要用原生窗口画遮罩 —— 那就变成了「一半 Tauri 一半 Win32」的缝合怪；
  - 「常驻 5MB、一按快捷键飙到 100MB」这种表现，和「极度轻量」的产品定位自相矛盾。

**结论：Tauri 适合「用 Web 技术栈快速做功能复杂的桌面应用」，不适合本项目。**

**C++ + Qt6 —— 唯一有竞争力的传统方案**

- 只用 `QtCore + QtGui + QtWidgets`，**绝不用 QML**（QML 引擎单独吃 20–30MB，是最大陷阱）。
- `QSystemTrayIcon` + 隐藏主窗口 + `RegisterHotKey`（不要用 QHotkey 这类第三方包，它内部也是 Win32 消息钩子，多一层没意义）。
- 卡点：
  - 动态链接时 Qt6Core/Gui/Widgets 三个 DLL 的共享页会算进工作集，任务管理器上看 30MB+，用户会认为你食言；
  - 想压到 15MB 以下必须静态链接，而 **LGPL 对静态链接要求提供可重链接的目标文件**，商业分发要么开源要么买授权；
  - `QImageReader::setScaledSize()` 对 PNG **是无效的**（只有 JPEG 走 libjpeg 的 DCT 缩放），做缩略图仍然要全图解码 —— 本方案的核心省内存技巧在 Qt 上要额外手写。
- **适用场景：团队只有 C++ 背景、不接受 Rust 学习成本。** 否则不是首选。

**C# + WinUI 3 —— 直接排除**

- WinUI 3 基于 Windows App SDK，即使空窗口也要 60MB 起步，自包含部署 80MB+。
- 托盘图标 WinUI 3 **原生不支持**，得引 `H.NotifyIcon` 再叠一层 Win32 互操作。
- 这个组合和「20MB」是两个世界的东西，不适合讨论。

### 1.4 推荐方案与理由

**Rust + 原生 Win32（windows-rs），即"取 Tauri 的 Rust 宿主层，扔掉 WebView"。**

理由按权重排序：

1. **内存确定性**。没有 GC、没有 JIT、没有浏览器引擎、没有 GPU 上下文。进程启动后就是 PE + CRT + 几个 GDI 句柄，3MB 级别，不存在"某次 GC 前突然涨到 40MB"的抖动。
2. **单文件交付**。`opt-level="z" + lto + strip + panic=abort` 后约 2–4MB，无 VC 运行库、无 Qt DLL、无 .NET 运行时、无 WebView2 依赖 —— 拷过去双击就能用，这是"轻量"的一半价值。
3. **本项目 UI 面积极小**。总共就 4 个窗口（托盘、遮罩、面板、设置），且都是**自绘**（列表、圆角、文字），GDI 完全够用。Rust 的 Win32 样板代码劣势在这个规模下可控。
4. **内存安全对 GDI/DIB 代码价值高**。截图工具的核心是裸指针 + 句柄（HDC/HBITMAP/HGLOBAL），C++ 里一个 `DeleteObject` 漏掉就是句柄泄漏，Rust 的 RAII 包装可以把这个错误类型从语言层面消灭。
5. **生态刚好够用**。PNG 编解码、配置序列化、注册表、资源嵌入都有成熟 crate，不需要造轮子。

**代价与缓解**：Win32 样板代码多、UI 迭代慢。缓解办法是 UI 只做"能看懂就行"的程度（自绘列表 + 系统字体），不追求花哨动效 —— 这恰好也是省内存的方向。

**备选路线**：若团队强 C++ 且能接受 LGPL 动态链接，走 Qt6 Widgets（严格禁用 QML），按 §3–§6 的设计思路同样成立，只是内存基线抬高 10MB。

## 2. 架构总览

### 2.1 进程 / 线程模型

```
sniptool.exe （单进程）
├─ 主线程：Win32 消息循环
│   ├─ 隐藏 message-only 窗口 (HWND_MESSAGE)  ← 托盘/热键/定时器消息都投递到这里
│   ├─ 框选遮罩窗口（按需创建/销毁）
│   ├─ 历史面板窗口（按需创建/销毁）
│   └─ 设置对话框（按需创建/销毁）
└─ 工作线程（仅清理任务时短时存在，THREAD_PRIORITY_IDLE，跑完即退）
```

- **不引入 async runtime**。全局热键、托盘、GDI 全是消息驱动，`GetMessage/DispatchMessage` 就是最合适的事件循环。
- **窗口即用即毁**。遮罩、面板、设置都遵循「打开→创建→关闭→`DestroyWindow`+释放位图」的完整生命周期，绝不做隐藏复用（隐藏窗口仍持有位图，是内存泄漏的常见来源）。

### 2.2 主流程

```
开机 → 读 config.json → 单实例检查 → 注册热键 → Shell_NotifyIcon 上托盘 → 消息循环
                                                                    ├─ WM_HOTKEY(capture) → 框选流程
                                                                    ├─ WM_HOTKEY(history) → 面板流程
                                                                    ├─ WM_TRAY              → 右键菜单
                                                                    └─ WM_TIMER(cleanup)    → 清理流程
```

### 2.3 消息与状态约定

| 常量 | 值 | 用途 |
|---|---|---|
| `WM_APP + 1` | 托盘回调消息 | `Shell_NotifyIcon` 的 `uCallbackMessage` |
| `WM_HOTKEY` id=1/2 | 系统消息 | 截图 / 历史面板 |
| `WM_TIMER` id=1 | 定时器 | 每日清理 |
| `WM_TIMER` id=2 | 定时器 | 面板悬停高亮防抖（可选） |

## 3. 核心设计 A：框选截图（零全屏缓冲）

### 3.1 关键取舍

主流做法是「先 BitBlt 整个虚拟桌面到一张 DIB，再把这张图当背景贴到全屏窗口上」——视觉上是"冻结画面"，但一张 4K 全屏 DIB 就是 **3840×2160×4 ≈ 33MB**，双屏 4K 直接 66MB，与内存目标正面冲突。

**本方案：遮罩挖洞 + 只抓选区。**

1. 不预抓屏。
2. 遮罩窗口用 `SetWindowRgn` 在窗口区域里**挖掉选区矩形**（`CombineRgn(..., RGN_DIFF)`），洞里是桌面真实内容，洞外是半透明暗色遮罩。
3. 鼠标抬起确认后，才从屏幕 DC `BitBlt` **仅选区那一块** —— 因为洞内不属于我们的窗口，抓到的是真实桌面内容，不会把自己的遮罩拍进去。

代价：遮罩期间背后画面是**实时的**（有动画时能看到变化），不如冻结画面"稳"。对截图工具而言这是可接受的，且避免了 33MB 瞬时占用。

若产品坚持要"冻结画面"，作为配置项 `freeze_screen: true` 提供，此时按显示器抓一张全屏 DIB（4K 约 33MB），并在编码完成前释放 —— 计入瞬时峰值，不计入常驻。

### 3.2 流程

```
WM_HOTKEY(capture)
  ├─ 快照当前前台窗口句柄（面板关闭后还原焦点用，可选）
  ├─ 计算虚拟桌面矩形：SM_XVIRTUALSCREEN / SM_YVIRTUALSCREEN / SM_CXVIRTUALSCREEN / SM_CYVIRTUALSCREEN
  ├─ 创建遮罩窗口：WS_POPUP | WS_EX_TOPMOST | WS_EX_TOOLWINDOW
  │    · 覆盖整个虚拟桌面（多屏含负坐标）
  │    · SetLayeredWindowAttributes(黑色, alpha=110, LWA_ALPHA)
  │    · SetWindowRgn(初始 = 空区域，即全遮罩)
  ├─ 鼠标左键按下 → 记录起点 → 开始拖拽
  │    · WM_MOUSEMOVE：重算选区 → 重建 region 挖洞 → 在选区外框画 1px 亮边 + 8 个控制点
  │    · 在选区右下方显示「宽 × 高」小标签（独立小窗口或自绘）
  ├─ 鼠标抬起 → 选区生效（< 4×4 px 视为误触，取消）
  ├─ Esc / 右键 → 取消，销毁窗口
  └─ Enter / 双击 → 确认
        ├─ 屏幕 DC BitBlt(选区) → 32bpp DIB Section
        ├─ 生成缩略图（见 §5.2，复用同一 DIB）
        ├─ PNG 编码 → 写 %TEMP%\MySnipTool\snip_YYYYMMDD_HHMMSS_mmm.png
        ├─ 写缩略图 → thumbs\<同名>.jpg
        ├─ 写剪贴板（CF_DIB + CF_PNG）
        └─ 释放 DIB / HDC / HBITMAP，销毁遮罩窗口，托盘气泡提示「已复制」
```

### 3.3 必须处理的平台细节

- **DPI**：manifest 声明 `PerMonitorV2`。否则在 125%/150% 缩放的显示器上，选区坐标与实际像素错位，截出来的图会偏移或缩小。
- **多屏负坐标**：副屏在主屏左侧/上方时坐标为负，所有坐标运算必须基于虚拟桌面原点，不能用 `(0,0)` 假设。
- **`CAPTUREBLT`**：BitBlt 时加此标志，否则抓不到分层窗口/带阴影的窗口内容。
- **遮罩窗口抢焦点**：需要 `SetForegroundWindow` 才能收到 Esc。但抢焦点会让原窗口失焦，介意的话用 `SetWindowsHookEx(WH_KEYBOARD_LL)` 只在遮罩期间临时挂键盘钩子（用完立刻卸）。
- **保护内容**：DRM 视频窗口、部分 UWP 应用 BitBlt 出来是黑图，无解，文档里注明即可。

## 4. 核心设计 B：历史面板的低内存缩略图

### 4.1 问题的本质

PNG 是 DEFLATE 压缩流，**不支持按目标尺寸解码**。想显示一张 4K 截图的缩略图，天真的做法是「解码全图（33MB RGBA）→ 缩放到 256px → 丢掉 33MB」。10 张就是 10 次 33MB 的往返，稍有不慎（比如把解码结果留在缓存里）就爆内存。

### 4.2 解法：缩略图在「截图那一刻」落盘

**关键洞察：截图时全分辨率 DIB 本来就在内存里，此时生成缩略图的边际成本几乎为零。**

```
截图确认时（DIB 已在手）：
  StretchBlt(HALFTONE)  →  256×144 的 DIB Section（147KB）
  → JPEG q=80 编码（约 8–15KB）→ 写 thumbs\<basename>.jpg
  → 释放
```

- 额外 CPU：< 5ms，用户无感。
- 额外内存：一次 147KB 的 DIB，复用已有 HDC，不增加峰值。
- 落盘占用：每张 10KB 左右，10 张 = 100KB，对 Temp 无压力。

### 4.3 面板打开时的内存账

```
面板尺寸 400×520，普通 popup 窗口（不用 UpdateLayeredWindow，省掉 830KB 后备位图）
  + 10 张缩略图 HBITMAP：256×144×4 = 147KB × 10 = 1.47 MB
  + 字体/画笔/双缓冲 DC：< 100 KB
  ─────────────────────────────────────────
  面板打开增量 ≈ 1.6–2.5 MB
```

对比「10 张原图」：4K 全图 = 33MB × 10 = **330MB**。差距 130 倍。

### 4.4 面板流程

```
WM_HOTKEY(history)
  ├─ FindFirstFileExW 枚举 %TEMP%\MySnipTool\*.png
  │    · 一次调用同时拿到 文件名 + 大小 + ftLastWriteTime
  │    · 不打开任何文件、不读一个字节
  │    · 按 mtime 降序，取前 10
  ├─ 逐项从 thumbs\ 找同名 .jpg
  │    · 命中 → WIC 解码为 HBITMAP
  │    · 缺失 → 现场解码原图生成（少数情况，仅 1 张，且用完即释放）
  │    · 原图已被外部清理 → 该行标记失效并静默跳过
  ├─ 创建自绘面板窗口：WS_POPUP | WS_EX_TOPMOST | WS_EX_TOOLWINDOW
  │    · 位置：光标所在显示器右下角内缩 24px
  │    · Win11 用 DWMWA_WINDOW_CORNER_PREFERENCE 拿原生圆角，Win10 用普通方角
  ├─ 逐行绘制：缩略图 + "今天 20:35:12" + 文件名 + 尺寸 KB
  ├─ 交互：↑↓ 选择 / Enter 打开 / Esc 关闭 / 点击某行打开 / 失焦自动关闭
  └─ 点击某行：
        ├─ 解码该原图 → HBITMAP → SetClipboardData(CF_DIB) + (CF_PNG)
        ├─ 释放位图
        └─ DestroyWindow 关闭面板，释放全部 10 张缩略图
```

### 4.5 必须遵守的纪律

- **禁止用 ListView / 列表控件**。`ListView` + `ImageList` 会额外分配内部缓存和 GDI 对象，一个 10 项列表的实测增量比自绘高一倍以上。整块自绘（一个窗口、一个 `WM_PAINT`、一个双缓冲 DC）最省。
- **禁止缓存跨会话保留**。面板关闭 → `DeleteObject` 所有 HBITMAP，不留静态缓存。
- **禁止预取**。不要"顺手把最近 10 张原图都解码好备用"。
- **弱引用式失效**：面板打开期间文件被外部删除，不要 panic，跳过即可（Temp 目录被 Storage Sense 清理是常态）。

## 5. 核心设计 C：每日定时清理

### 5.1 为什么不用任务计划程序

| 方案 | 常驻开销 | 优点 | 缺点 |
|---|---|---|---|
| Windows 任务计划程序 | 0 | 进程不在也能跑 | 需注册计划任务（用户可见、可能被杀软/组策略拦）、调试麻烦、与主程序状态不同步 |
| 独立清理线程 + `CreateWaitableTimerExW` | 线程栈保留 1MB / 实提交 ~64KB | 精确 | 多一个线程，需手动管理生命周期 |
| **消息循环 `SetTimer`（推荐）** | **~0** | 零线程、零句柄额外开销，与主循环天然串行 | 进程必须存活（本工具恰好是常驻的） |

**结论：用主消息循环的 `SetTimer`。** 本工具 7×24 常驻，恰好是任务计划程序唯一优势的反面。

### 5.2 调度策略

```
启动时：
  last_cleanup = state.json 里的时间戳
  if now - last_cleanup > 24h → 立即补跑一次（后台低优先级线程）

常驻：
  ms = 距离下一个 03:00 的毫秒数
  SetTimer(hwnd, TIMER_CLEANUP, ms, None)

WM_TIMER(TIMER_CLEANUP)：
  run_cleanup()
  SetTimer(hwnd, TIMER_CLEANUP, 下一个 24h 的毫秒数, None)   ← 每轮重新计算，天然抗漂移
```

**睡眠/休眠处理**：`SetTimer` 在系统睡眠期间不累积，唤醒后可能延迟数小时才触发。因此每次 `WM_TIMER` 里先用 `GetTickCount64()` 与上次触发时的值对比，若实际间隔 > 26h 说明机器睡过，立刻补跑并修正基准。

### 5.3 清理算法（纯元数据，零图像读取）

```
fn run_cleanup(dir: &Path, retention_hours: u64) -> CleanupStat {
    let now = SystemTime::now();
    let mut stat = CleanupStat::default();

    // 一次 FindFirstFileW / FindNextFileW 遍历，拿全 名字+大小+ftLastWriteTime
    // 不 CreateFile、不 ReadFile、不 mmap —— 全程只有目录项元数据
    for entry in enumerate_dir(dir) {
        if entry.is_directory { continue }              // 跳过 thumbs 子目录本身
        if !is_our_own_file(&entry.name) { continue }    // 安全护栏，见下

        let age = now - entry.last_write_time;
        if age <= retention_hours {
            stat.kept += 1;
            continue;
        }

        match delete_file(entry.path) {
            Ok  => stat.deleted += 1,
            Err => stat.skipped += 1,                    // 被占用/只读 → 忽略，下轮再试
        }
    }

    // 顺带清理 thumbs\ 下孤儿缩略图（原图已不存在的）
    sweep_orphan_thumbs();

    state.last_cleanup = now;
    stat
}
```

**内存特征**：遍历过程只持有当前一个目录项结构（几百字节）+ 一个路径字符串缓冲（复用同一个 `Vec<u16>`，容量固定 512，避免每项重新分配）。峰值增量 < 32KB，与文件数量无关。**图像数据一个字节都不进内存。**

### 5.4 必须做的安全护栏

1. **文件名白名单**：只删匹配 `snip_*.png` / `snip_*.jpg` 的文件。用户若把 `temp_dir` 配成了别的目录，也不会误删无关文件。
2. **路径校验**：启动时规范化 `temp_dir`，拒绝包含 `..`、拒绝是驱动器根目录、拒绝解析后落在 `C:\Windows`、`C:\Program Files` 等系统路径下。
3. **不跟随符号链接 / 目录联接**：遇到 `FILE_ATTRIBUTE_REPARSE_POINT` 一律跳过，防止 junction 把删除操作引到别处。
4. **写入用「临时名 + 原子重命名」**：`snip_xxx.tmp` → `MoveFileExW(..., MOVEFILE_REPLACE_EXISTING)`，避免清理线程删掉正在写入的半成品（同理，清理只删 `.png`，不碰 `.tmp`）。
5. **失败静默**：任何单项失败都不中断整体流程，只计数。清理是"尽力而为"的后台行为，不需要弹窗打扰用户。

### 5.5 「每日」与「24 小时」的语义统一

用户需求里两个词有轻微矛盾：**每日执行一次**、**删除超过 24 小时的**。

实现取交集：每日 03:00 跑一次 + 启动时补跑，每次删除 `mtime` 早于「当前时间 - 24h」的文件。效果是「文件存在时长严格 24–48h 之间被删」。若产品希望更精确（严格 24h 内必删），把定时器改成**每小时**跑一次同样的判断，成本只有一次目录遍历（100 个文件 < 1ms），这也是我推荐的稳健默认值。

## 6. 内存预算表

### 6.1 常驻（托盘空闲态，验收口径）

| 项 | 估算 |
|---|---|
| PE 映像 + CRT + 堆基线 | 2.5 – 4.0 MB |
| 隐藏 message-only 窗口 + 托盘图标（多尺寸 ico） | < 0.2 MB |
| 配置/状态结构体（JSON 解析后） | < 20 KB |
| 热键注册 + 定时器 + 消息队列 | < 10 KB |
| **合计（私有工作集）** | **3 – 5 MB** |
| **合计（含共享 DLL 页的工作集）** | **8 – 14 MB** |

### 6.2 瞬时增量（不进常驻口径，用完即释放）

| 场景 | 增量 | 释放时机 |
|---|---|---|
| 框选遮罩（region 挖洞，无位图） | +0.1 MB | 选区确认/取消 |
| 确认后编码（选区 W×H×4） | +3 MB（1024×768）～ +33 MB（4K 全屏） | PNG 落盘后立刻 |
| 历史面板 | +1.6 – 2.5 MB | 面板关闭 |
| 点击历史项写剪贴板 | 同编码（单张 W×H×4） | `SetClipboardData` 后立刻 |

> 剪贴板里的位图由**系统剪贴板堆**持有，不计入本进程私有内存 —— 这是 Windows 的设计，不是作弊。
> 若要把 4K 全屏选区的最坏峰值也压到 20MB 以内：改为**分块编码**（逐行 strip 喂给 PNG encoder，需换用 WIC 的流式编码器），或限制单次选区最大面积。属于 v1.1 优化项。

### 6.3 反模式清单（写代码时逐条对照）

- ❌ 引入 `tokio` / `async-std`：单是 runtime 就 3–8MB。
- ❌ 引入 `egui` / `slint` / `iced`：GPU 上下文 + 框架状态，20–60MB 起。
- ❌ 全局 `HashMap<String, DynamicImage>` 做图片缓存。
- ❌ 用 `Vec<u8>` 把整张 PNG 编码结果读进内存再 `fs::write` —— 应直接 `BufWriter<File>` 流式写。
- ❌ 面板窗口 `ShowWindow(SW_HIDE)` 复用而不销毁。
- ❌ GDI 对象泄漏：每个 `CreateCompatibleDC` 必须配 `DeleteDC`，每个 `CreateBitmap`/`CreateFont` 必须配 `DeleteObject`。用 RAII wrapper 强制。

**`windows-sys` 需要的 feature 清单**（精确到能编译的最小集）：

```
Win32_Foundation
Win32_UI_WindowsAndMessaging      // 窗口/消息/菜单/托盘回调
Win32_UI_Shell                    // Shell_NotifyIcon
Win32_UI_Controls                 // 托盘图标加载（可选）
Win32_Graphics_Gdi                // BitBlt / StretchBlt / DIB / 字体
Win32_Graphics_Dwm                // Win11 圆角
Win32_Graphics_Imaging            // WIC 编解码（若不用 image crate 则必需）
Win32_System_DataExchange         // 剪贴板
Win32_System_Memory               // 全局内存（CF_DIB 用）
Win32_System_Registry             // 自启
Win32_System_LibraryLoader        // 资源/图标
Win32_System_Threading            // 互斥体（单实例）
Win32_System_SystemInformation    // 虚拟屏幕尺寸
Win32_UI_Input_KeyboardAndMouse   // RegisterHotKey / MOD_* / VK_* / SetCapture
```

**明确不引入**：`tokio`、`rayon`、`tauri`、`wry`、`egui`、`slint`、任何 WebView 绑定。

> **踩过的坑 1（Spike 1 实际编译错误）**：feature 的归属不是按「函数在哪个头文件」划分的，而是按**参数/字段引用了哪个模块的类型**。
> `RegisterClassW` 的参数是 `*const WNDCLASSW`，而 `WNDCLASSW` 含 `HBRUSH`/`HICON`/`HCURSOR` 三个 GDI 类型，于是 windows-sys 把 `WNDCLASSW` 和 `RegisterClassW` 一起放进了 **`Win32_Graphics_Gdi`** 门后。
> 只开 `Win32_UI_WindowsAndMessaging` 时，`UnregisterClassW` 能找到、`RegisterClassW` 找不到 —— 这个不对称就是判断依据。
> 结论：**`Win32_Graphics_Gdi` 从第一行代码起就是必需项**，不是 Spike 2 才需要。

> **踩坑 2（Spike 2）**：更反直觉的一批归属 —— 都是 user32 的函数，却不在 `WindowsAndMessaging` 里：
>
> | 符号 | 实际模块 | 需要的 feature |
> |---|---|---|
> | `RegisterHotKey` / `UnregisterHotKey` / `MOD_*` / `VK_*` | `UI::Input::KeyboardAndMouse` | `Win32_UI_Input_KeyboardAndMouse` |
> | `SetCapture` / `ReleaseCapture` / `SetFocus` | `UI::Input::KeyboardAndMouse` | 同上 |
> | `BeginPaint` / `EndPaint` / `PAINTSTRUCT` / `DT_*` | `Graphics::Gdi` | `Win32_Graphics_Gdi` |
> | `SetWindowRgn` / `UpdateWindow` / `InvalidateRect` / `GetUpdateRect` | `Graphics::Gdi` | `Win32_Graphics_Gdi` |
>
> 排查方法：`grep -rn "fn RegisterHotKey" ~/.cargo/registry/src/*/windows-sys-*/src/Windows/Win32`，
> 别猜。

## 10. 验证计划（先花半天做技术验证，再写业务代码）

内存目标必须**在目标机型上实测**，不能靠估算验收。建议按下列顺序做 4 步 spike，每步都跑 `Get-Process` 采样：

```powershell
Get-Process sniptool | Select-Object `
  @{n='工作集(MB)';e={[math]::Round($_.WorkingSet64/1MB,1)}}, `
  @{n='私有(MB)';e={[math]::Round($_.PrivateMemorySize64/1MB,1)}}, `
  @{n='句柄';e={$_.HandleCount}}, `
  @{n='GDI对象';e={(Get-Process -Id $_.Id).HandleCount}}
```

| 步骤 | 内容 | 验收点 |
|---|---|---|
| Spike 1（0.5h） | 空壳托盘程序：隐藏窗口 + 托盘图标 + 消息循环 | 空闲私有 ≤ 5MB，工作集 ≤ 12MB；连续 10 分钟无增长（无泄漏） |
| Spike 2（2h） | 加 `RegisterHotKey` + 遮罩 region 挖洞 + 拖拽画框 | 遮罩打开时增量 ≤ 0.5MB；Esc 取消后归零；GDI 对象数回到基线 |
| Spike 3（2h） | 加 BitBlt 选区 + PNG 落盘 + 剪贴板 + 缩略图 | 4K 全屏截图峰值 ≤ 40MB 且落盘后回落；画图/微信/Word 三处粘贴均正常 |
| Spike 4（2h） | 加历史面板（10 项自绘）+ 点击回写剪贴板 | 面板打开增量 ≤ 3MB；关闭后回落至基线 ±0.5MB；反复开关 100 次无累积增长 |

**Spike 1 是最关键的**：如果空壳托盘都压不到 6MB，说明技术栈选错了，此时改 Qt 的成本最低。

### 10.1 泄漏复现手法

轻量工具最常见的失败不是"启动就 30MB"，而是"跑一天涨到 80MB"。验收必须包含**长稳测试**：模拟 200 次截图 + 200 次开关面板，采样曲线必须回到基线。GDI 对象数（任务管理器"详细信息"页的「GDI 对象」列）是比内存更灵敏的泄漏指标 —— 稳定在 40–60 个，只增不减就是漏了。

## 11. 遗留问题（需产品确认）

1. **内存口径**：20MB 指私有工作集还是任务管理器显示的工作集？本方案两种都过，但 Qt 方案在工作集口径下会失守，需提前统一。
2. **Ctrl+Alt+A 冲突**：这是国内环境最可能被 QQ/微信抢占的组合。是否接受"首次启动若注册失败，弹一次引导让用户改绑"的交互？
3. **冻结画面**：`freeze_screen` 默认关闭（省 33MB），但是否要在设置里暴露给用户？暴露则需接受 4K 下 33MB 瞬时峰值。
4. **是否需要 OCR / 标注（箭头、马赛克）**：若 v2 要做标注，框选遮罩需改为可编辑画布，届时内存与代码结构都会变化，现阶段设计需预留（遮罩窗口保留一个"编辑态"扩展点）。
